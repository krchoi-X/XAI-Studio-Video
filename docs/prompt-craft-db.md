# 프롬프트 작성법 DB (Prompt Craft Database)

v1.6 — 2026-10-01. 코퍼스 76개 레퍼런스의 분석에서 추출.
연출기법 DB가 "무엇을 보여줄지"라면, 이 DB는 "모델에게 어떻게 말할지"다.
레이어 구분: **구조**(프롬프트의 뼈대) / **물리 서술**(움직임을 말하는 법) /
**락**(일관성 고정) / **네거티브**(막는 법) / **워크플로우**(만드는 과정).

신뢰도: ★★★(독립 3건 이상) / ★★(2건) / ★(1건, 추가 검증 필요).
★ 1개는 "통한 사례가 있다"로 읽을 것.

## 사용법 (다른 AI용)

1. 프롬프트를 쓸 때 아래 문제 인덱스에서 현재 막히는 지점을 찾는다.
2. 해당 P-기법의 Control Level대로 적용한다.
3. **연출기법 DB와 함께 쓸 것**: 보여줄 것(연출)이 먼저, 말하는 법(프롬프트)이
   다음. 연출이 없으면 프롬프트 기법은 빈 껍데기다.

## 문제 인덱스

| 문제 | 후보 기법 |
|---|---|
| 프롬프트가 길어지면 모델이 앞부분을 잊는다 | P-01 섹션 아키텍처, P-20 마스터 스위치 |
| 타임코드를 써도 모델이 안 지킨다 | P-03 비트표는 순서만, P-02 백분율 페이즈 |
| 물리 장면이 어색하게 나온다 (물·불·타격) | P-06 Trace-first, P-07 상태 전이 체인, P-13 capability 언어 |
| 손-물체 접촉이 깨진다 | P-09 boundary lock |
| 표정·모션이 로봇 같다 | P-12 반로봇 불규칙성, P-10 반응 메뉴 |
| 금지어(negative prompt)를 써도 안 막힌다 | P-14 POSITIVE LOCKS, P-21 실패 출처 네거티브 |
| 캐릭터 얼굴이 컷마다 바뀐다 | P-16 캐릭터 락, P-15 레퍼런스 역할 분리 |
| 옷이 컷마다 바뀐다 | P-17 아웃핏 락 |
| 소품 총량이 안 맞는다 (총알, 적의 수) | P-18 수량 경제 |
| 복선 소품이 갑자기 튀어나온다 | P-19 Pre-planted device |
| 판타지가 싸구려 CG처럼 나온다 | P-23 Grounded negatives |
| 모델마다 같은 프롬프트가 다르게 먹는다 | P-26 모델별 어댑터 |
| 짧은 아이디어를 긴 프롬프트로 못 늘리겠다 | P-27 LLM 확장 워크플로 |
| 고해상도로 뽑으면 돈이 너무 든다 | P-25 Resolution stepping |
| 브이로그인데 컷마다 할 말이 없다 | P-28 컷별 대사 (연출 DB T-01과 연결) |

## A. 프롬프트 구조

### P-01. 섹션 아키텍처 (Section Architecture)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 프롬프트가 길어지면 모델이 앞을 잊고 뒤를 날림
- **기법**: 고정 섹션 순서 — CAMERA / LOOK / STYLE / REFERENCE IMAGE /
  OUTFIT / SETTING / STORYBOARD / IMPORTANT. 각 섹션은 한 가지 역할만.
  IMPORTANT를 마지막에 두어 마스터 스위치로 (P-20).
- **코퍼스 근거**: #64 (8컷 스토리보드가 프레임에 그대로 반영된 완성형) ★,
  #38·#40·#45 (CHASE 계열 동일 구조) ★★
- **금기**: 섹션을 섞지 말 것. STORYBOARD 안에 LOOK을 쓰면 묻힘.
- **LOCK 명명법 변형** (#73, strengthen): EXACT ORDER +
  ERA LOCK + CAMERA STYLE + CONTINUITY + FINAL FEEL. LOCK을
  섹션 이름에 붙이면 모델이 해당 잠금을 섹션 단위로 지킴.
  ERA LOCK은 시대 고증의 포지티브+네거티브 병기
  ("No smartphones, modern LED screens, AirPods...").

### P-02. 백분율 페이즈 (Percentage Phases)

- **Control Level**: Soft Guidance
- **해결하는 문제**: "0–4초" 같은 절대 시간을 모델이 안 지킴
- **기법**: 페이즈를 백분율로 지정 (0–25·25–55·55–70·70–100).
  모델은 절대 시간은 못 지켜도 순서는 지킴 (P-03).
- **코퍼스 근거**: #41 (4개 페이즈 경계가 프레임 4장과 맞아떨어짐) ★
- **금기**: 백분율+절대 시간 혼용 금지. 하나만.

### P-03. 비트표는 순서만 (Order-Only Beats)

- **Control Level**: Hard Lock (프롬프트 작성 규칙)
- **해결하는 문제**: 타임코드 기반 스토리보드가 매번 어긋남
- **기법**: 비트표에 절대 시간을 쓰지 않는다. 순서는 유지되나 압축·
  드리프트가 발생함을 전제로 짠다. 시간 약속은 백분율(P-02)로만.
- **코퍼스 근거**: #31·#37 (프레임 검증으로 드리프트 확인) ★★
- **금기**: "~4s" 같은 표기는 순서 힌트로만. 지키라고 하면 안 됨.

### P-04. 샷별 헤드카운트 (Shot-Level Headcount)

- **Control Level**: Hard Lock
- **해결하는 문제**: 컷마다 인원수가 바뀌거나 엑스트라가 끼어듦
- **기법**: 각 샷에 "화면에 정확히 N명"을 명시. 인원수는 연속성의
  가장 싼 락.
- **코퍼스 근거**: #33·#37 ★
- **금기**: 배경 인파가 필요하면 "배경 N명"을 따로 명시.

### P-05. 모듈러 참조 (Coupling)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 같은 텍스트 블록을 매번 반복해서 길어짐
- **기법**: 공유 블록을 참조로 — "Coupling: ON (existing speech_coupling
  text applies)". 마스터 스펙 → 참조 구조. 사용자의 XAI-Studio-Video
  철학과 수렴.
- **코퍼스 근거**: #41 ★
- **금기**: 참조 대상이 없는데 ON 하면 안 됨. 모델이 못 읽는 참조는
  독이 됨.

## B. 물리 서술

### P-06. Trace-first physics writing

- **Control Level**: Soft Guidance
- **해결하는 문제**: "무거운 타격" 같은 추상어가 모델에게 안 먹음
- **기법**: 힘의 이름 대신 시각적 증거 5종으로 서술 —
  Trajectory(궤적) / Momentum(운동량) / Resistance(저항) /
  Impact(충돌) / Weight Transfer(무게 이동). 보이는 것만 쓴다.
- **코퍼스 근거**: #5·#8·#26·#33·#34 ★★★
- **충격 프레임 시간 명세** (#76, strengthen): 0.05/0.1/0.15초
  등급 + 레이어 스택 순서로 서술. "0.05초: 흑백 수묵 충격
  프레임 → 부분 반전 → 카메라 짧은 축 흔들림 → 먹점과 수무가
  튐다". 시간+순서가 있으면 모델이 필터처럼 남발하지 않음.
- **금기**: 뉴턴 단위, "강하게" 같은 측정 불가 형용사.

### P-07. 상태 전이 체인 (State Transition Chain)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 액션의 전조·충돌·결과가 따로 놀음
- **기법**: anticipation → contact → consequence를 끊지 않고 기술.
  "팔을 뒤로 → 주먹이 닿음 → 상대가 뒤로 밀림" 한 문장 사슬.
- **코퍼스 근거**: #8·#26·#33·#35·#36 ★★★
- **금기**: contact만 쓰고 전후를 생략하면 텔레포트처럼 보임.

### P-08. 상태 구별화 (Named Failure States)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 같은 물리 오류가 반복되는데 매번 길게 설명해야 함
- **기법**: 물리 상태 오류에 이름을 붙여 네거티브 어휘로 등록.
  예: buoyancy_zerogravity_confusion (부력이 무중력처럼 보이는 오류).
- **코퍼스 근거**: #8·#35 ★★
- **금기**: 이름만 만들고 정의를 안 쓰면 모델이 못 알아먹음.

### P-09. Boundary lock

- **Control Level**: Hard Lock (접촉 장면에 한함)
- **해결하는 문제**: 손-물체 접촉부가 녹아내림
- **기법**: 접촉하는 물체들의 물리적 경계 유지를 선언.
  "손–스틱–드럼헤드–심벌의 경계 유지". 닿는 것들의 목록을 명시.
- **코퍼스 근거**: #34 ★
- **금기**: 경계만 선언하고 접촉 순서를 안 쓰면 반쪽짜리.

### P-10. 반응 증거 메뉴 (Reaction Evidence Menu)

- **Control Level**: Creative Freedom
- **해결하는 문제**: 타격 반응이 매번 똑같이 나옴
- **기법**: 반응을 메뉴에서 골라 조합 — 비틀거림/주저앉음/표정 일그러짐
  등 13종 어휘표에서 선택. 반응의 다양성이 곧 타격감.
- **코퍼스 근거**: #26 ★
- **금기**: 메뉴를 다 쓰면 산만. 1타격당 1–2개.

### P-11. 해부학 앵커 (Anatomy Anchors for Morphs)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 변신·성장 장면에서 몸이 녹음
- **기법**: 모핑 시 해부학 기준점을 기술 — 척추 연장, 무게중심 이동,
  어깨선 상승. 몸의 "뼈대"가 먼저, 살은 다음.
- **코퍼스 근거**: #36 ★
- **금기**: 앵커 없이 "커진다"만 쓰면 풍선처럼 부풀음.

### P-12. 반로봇 불규칙성 (Anti-Robot Irregularity)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 모션이 완벽해서 가짜 같음
- **기법**: "완벽히 매끄럽거나 동일하거나 로봇처럼 동기화된 모션 금지"를
  명시. 불완전함을 스펙으로 (연출 DB T-23과 같은 혈통).
- **코퍼스 근거**: #34 ★
- **금기**: 불규칙성의 방향을 안 정하면 그냥 흔들림.

### P-13. Capability-calibrated 언어

- **Control Level**: Hard Lock (프롬프트 작성 규칙)
- **해결하는 문제**: 모델이 할 수 없는 지시를 내림
- **기법**: 모델이 할 수 있는 말로만 쓴다. 측정 불가능한 물리량 대신
  관찰 가능한 서술. "할 수 있는 말"의 기준은 프레임 검증.
- **코퍼스 근거**: #33 ★
- **금기**: "마음속으로" 같은 내면 묘사. 카메라는 마음을 못 찍음.

## C. 락 (일관성 고정)

### P-14. POSITIVE LOCKS

- **Control Level**: Hard Lock
- **해결하는 문제**: 네거티브 프롬프트가 안 먹음
- **기법**: 금지어보다 "이것은 고정" 선언을 우선. "엠블럼의 기하학적
  동일성 유지", "종목당 1명". 막는 말보다 묶는 말이 강함.
- **코퍼스 근거**: #33·#37 ★★
- **금기**: 락을 너무 많이 걸면 모델이 굳음. 핵심만.

### P-15. 레퍼런스 역할 분리 (Reference Role Separation)

- **Control Level**: Hard Lock
- **해결하는 문제**: 레퍼런스 이미지를 주면 스타일까지 따라옴
- **기법**: 레퍼런스 이미지는 기능별 1역할만 —
  identity-only / style-only / location-only. 역할을 명시하지 않은
  레퍼런스는 전부 훔쳐감.
- **코퍼스 근거**: #4·#9·#16 ★★
- **비디오 역할 + 충돌 우선순위** (#74, strengthen): 비디오도
  역할 분리 대상 — @视频1=동작·카메라·편집 전용, "얼굴·헤어·
  의상은 상속 금지"를 명시. 충돌 시 우선순위 선언: 외모·의상→
  이미지, 동작·렌즈→비디오, 로고→이미지3. "不是重新编排剧情"
  (재현이지 재해석이 아님) 같은 작업 유형의 네거티브 선언도 함께.
- **금기**: 1이미지 다역할. 욕심내면 셋 다 깨짐.

### P-16. 캐릭터 락 (Character Lock)

- **Control Level**: Hard Lock
- **해결하는 문제**: 컷마다 얼굴이 바뀜
- **기법**: 캐릭터 시트(이미지)를 선행하고 "같은 인물이 매 샷에"를
  선언. 얼굴·헤어·체형을 각각 명시. 멀티컷이면 컷마다 재확인 문구.
- **코퍼스 근거**: #52 (시트 선행 파이프라인) ★, #16·#64 ★★
- **미세 식별자 락** (#74, strengthen): 점·문신은 위치·좌우·
  개수를 잠근다. "痣不要移动到嘴角，不要左右镜像，不要在
  特写中消失" / "禁止纹身转移到左臂，禁止左右手臂同时出现
  纹身". 거울 반전이 얼굴을 뒤집는 실패 모드. 헤어도 정체성
  (길이·색 유지) + 물리 (발근 안정, 관성, 얼굴 관통 금지)로
  함께 잠근다.
- **2인 락 (FRIEND LOCK)** (#77, strengthen): 주인공 외
  동행 인물도 별도 락 — "The SAME Japanese female friend stays
  with her throughout". 각자 얼굴·헤어·의상·가방을 따로 잠근다.
- **금기**: 텍스트로만 얼굴을 고정하려 하지 말 것. 이미지가 본체.

### P-17. 아웃핏 락 (Outfit Lock)

- **Control Level**: Hard Lock
- **해결하는 문제**: 컷마다 옷이 바뀜
- **기법**: 의상을 색·핏·소재까지 명시하고 "전편 동일한 의상"을 선언.
  "no jacket, no jewelry" 같은 제외 목록도 함께.
- **코퍼스 근거**: #64 ★
- **금기**: 의상 묘사가 캐릭터 묘사보다 길어지면 안 됨.

### P-18. 수량 경제 (Quantity Economy)

- **Control Level**: Hard Lock (수량이 바뀌는 장면에 한함)
- **해결하는 문제**: 총알 수, 적의 수가 컷마다 바뀜
- **기법**: 총량을 수식으로 명시 — "six rounds, no reload" →
  two dry clicks → holster. 증식하는 적은 1→2→4→5→6→7→(3 fall)→4→1
  같은 산술로. "맞은 적만 나뉜다" 같은 규칙도 함께.
- **코퍼스 근거**: #46 ★★
- **금기**: 수식을 쓰고 시각적 단서를 안 주면 모델이 못 셈.

### P-19. Pre-planted device (복선 소품)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 해결책 소품이 갑자기 튀어나와서 억지 같음
- **기법**: 소품은 처음부터 있었지만 "concealed by hull and framing
  until Shot 11" — 프레임 아래에 숨겨뒀다고 명시. 복선은 숨기는 것.
- **코퍼스 근거**: #46 ★
- **금기**: 숨긴다고 안 보이면 관객이 못 찾음. 한 번은 흘끗 비출 것.

### P-20. IMPORTANT 마스터 스위치 (Logic Rule)

- **Control Level**: Hard Lock
- **해결하는 문제**: 섹션별 지시가 서로 충돌함
- **기법**: 프롬프트 끝에 한 줄 마스터 스위치 —
  "Keep logical consistency in wardrobe, props, locations, and
  action continuity across all shots." 전체를 관통하는 최상위 명령.
- **코퍼스 근거**: #47 (LOGIC RULE) ★, #64 (IMPORTANT) ★
- **금기**: 마스터 스위치가 섹션 지시와 모순되면 안 됨.

## D. 네거티브

### P-21. 실패 출처 명시 네거티브

- **Control Level**: Soft Guidance
- **해결하는 문제**: 네거티브가 추상적이라 안 먹음
- **기법**: 네거티브에 "어떤 실패에서 왔는지"를 기록.
  "no X — [실패 사례: #24에서 Y가 발생]". 실패의 이름을 아는 것이
  방지의 시작.
- **코퍼스 근거**: #4·#19·#24·#25 ★★★
- **실패 카탈로그형** (#74, strengthen): 섹션 八처럼 관찰된
  실패 모드를 항목별로 나열 — "禁止纹身换边" (문신 좌우 바뀜),

  "금지 X"가 목격된 실패의 이름.
- **금기**: 실패 출처를 적는 데만 길어지면 안 됨. 한 줄.

### P-22. 관계형 부정문 (Relational Negatives)

- **Control Level**: Soft Guidance

### P-23. Grounded negatives

### P-24. 모션 네거티브 구체화 (Embodied Motion Negatives)

- **금기**: 리스트가 길어지면 모델이 위축됨. 핵심 4–5개.

### P-27. LLM 확장 워크플로

### P-28. 컷별 대사 (Dialogue per Cut)

- **Control Level**: Soft Guidance
- **해결하는 문제**: 브이로그·토크 장면에서 컷마다 할 말이 없음
- **기법**: 스토리보드의 컷마다 대사를 붙인다. 대사가 각 컷의
  존재 이유가 됨. 연출 DB T-01(대사 브릿지)과 연결 — 대사는
  브릿지이자 앵커.
- **코퍼스 근거**: #64 ★
- **금기**: 대사가 동작 설명이 되면 안 됨. 말은 말답게.

### P-29. 상태 락 (State Lock: 상처·손상)

- **Control Level**: Hard Lock
- **해결하는 문제**: 액션물에서 상처·손상이 증식·소멸·이동함
- **기법**: 상처를 타임스탬프+부위+개수로 지정한다. "칼끝이
  하린의 얼굴에 정확히 세 개의 얕은 상처 — 뺨(0-3초),
  턱선(9-12초), 이마 옆(18-21초). 각 상처에서 가는 핏줄기가
  배어나고... 위치·개수 고정, 증식·소멸·이동 금지". 출혈의
  정도까지 ("가는 핏줄기와 핏방울 수준") 명시. 상대의 상처도
  따로 고정 ("상대의 뺨 상처는 한 개").
- **코퍼스 근거**: #65 ★★★ (#48의 damage persistence 계승.
  프레임 대조로 세 번째 상처(관자놀이 핏줄기) 렌더 확인)
- **금기**: "상처가 남는다" 같은 추상 서술은 안 먹음. 개수·위치·
  시간을 숫자로.

### P-30. 소품 상태 원장 (Prop State Ledger)

- **Control Level**: Hard Lock
- **해결하는 문제**: 씬이 넘어가면 소품이 순간이동·물질화·소실됨
- **기법**: 모든 소품에 대해 씬별 상태 행을 적는다 —
  위치·소지자·내용물. "흰 비닐봉지: S1 왼손(빈 상태)→S2 왼손→
  S3 포옹 시 왼 손목에 건다→S4 오른손으로 복숭아 1개를 넣어
  왼손→S5 왼손→S6 왼손. 동전: 숄더백 앞주머니→S2 오른손→
  점원에게. 페이스트리: S2 오른손→S5 오른손에서 먹는 중."
  P-29(상처 락)의 소품 버전. "pays with coins"처럼 WHAT만
  쓰면 모델이 HOW(어디서 꺼냈는지)를 생략하고 손에 물질화함 —
  P-06 Trace-first의 소품 적용.
- **코퍼스 근거**: #66 ★ (신규. 원장 없이 6개 파탄 발생)
- **금기**: "가방을 들고 있다" 같은 현재형 서술 1회로 끝내지
  말 것. 상태는 씬마다 다시 선언해야 carryover됨.
- **사물 생애주기** (#73, strengthen): "The purchased
  ingredients must be the same ones used for cooking and served
  at dinner." 장보기→씻기→조리→상차림 — 소품이 비트를
  넘어갈 때 변형(이력)을 거치면 물질화가 아님. 원장에 상태가
  아니라 이력을 적는 형태.
- **클립 단위 확장** (#71, strengthen): 30초짜리 2편을 따로
  생성해 이어붙일 때, 뒤편 프롬프트에 앞편의 끝 상태를 그대로
  적는다 — "같은 방파제, 젖은 머리와 의상, 적은 화면 오른쪽".
  씬→씬 carryover와 같은 원리의 클립→클립 적용.

### P-31. 스케일 기준물 명세 (Scale Anchoring)

- **Control Level**: Hard Lock
- **해결하는 문제**: "멀리", "크게" 같은 추상 형용사를 쓰면
  모델이 거리는 좁히고 몸집은 작아지는 사고를 냄 (#71의
  관찰된 실패 모드)
- **기법**: 거리와 크기를 화면 속 눈에 보이는 사물로 못박는다.
  거리 = "방파제 네 개 길이", 크기 = "등대가 허벅지에 닿는
  몸집". 프롬프트의 3분의 1을 스케일 설명에 할당. 액션
  장르뿐 아니라 적용 가능.
- **코퍼스 근거**: #71 ★ (신규)
- **금기**: 추상 형용사("거대하게", "아주 멀리") 단독 사용.
  기준물 없는 스케일 서술은 모델이 축소하는 쪽으로 회귀함.
