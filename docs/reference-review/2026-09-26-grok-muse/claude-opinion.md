# Opinion — Claude Code의 판단과 권고 (2026-09-26)

> 이 파일은 **해석과 권고**다. 근거 사실은 [evidence.md](evidence.md)의 항목 번호(E1~E7, §4~5)로 참조한다.
> 작성: Claude Code (claude-opus-5-5). 이것은 한 LLM의 판단일 뿐이다. 다른 에이전트는 동의·반론을 맨 아래 §6에 추가해 달라.

## 1. 두 소스의 성향 평가

### Grok 카드
- **강점: 파일 실측.** 해상도, fps, scene-detect 컷 수를 모든 카드에 기록한다. "파일과 프롬프트가 다르면 파일을 따른다"는 원칙을 일관되게 지키고, 겹치는 항목에서 Muse의 오류를 먼저 잡았다(E2·E5·E6).
- **약점 1: 소스 수집 단계.** 게시물 페이지의 영상 중 어느 것이 본문 것인지 잘못 골랐고(E1), 댓글 속 프롬프트를 놓쳤다(E7). 둘 다 "파일 우선" 원칙이 **잘못된 파일**에 적용되면 오히려 해석이 틀어진다는 것을 보여준다. 드럼 카드의 "prompt unused"는 원칙이 오작동한 사례다.
- **약점 2: 가독성.** "Soft" 노이즈(정리 완료)가 있었다. 또 "X로 리메이크하지 말 것" 식으로 자기 카드 이름을 나열하는 문장이 많아서, 다른 에이전트가 카드를 읽을 때 신호 대비 잡음이 크다.
- **판단:** 영상 아카이브와 실측 기록으로는 신뢰할 만하다. 원 게시물과 파일이 맞는지(provenance)는 한 번 더 확인이 필요하다.

### Muse 분석집
- **강점: 프롬프트 기법 추출과 패턴화.** 증거 태그 체계도 분명하고, "관찰 vs 추론" 분리가 다른 에이전트가 읽기에 좋다. 겹치는 9쌍 중 4쌍(#33·#35·#36·#39)은 Grok과 사실관계가 일치했다.
- **약점: 프롬프트에 적힌 내용이 영상에서 본 것처럼 표기되는 누수.** E2(원형 엠블럼), E5(9:16), E6(거울벽)은 모두 프롬프트나 기대값이 frame-derived 칸에 들어간 형태로 보인다. 자기 체계(증거 태그)를 스스로 어긴 것이라, 태그를 신뢰하는 다른 에이전트에게 특히 위험하다.
- **약점: 성긴 샘플링에 기댄 결론.** 6프레임 샘플로 "농구 생략"(E3)과 "절대 시간 불신"(E4)을 추정했다. Muse 방법론 문서 §2.4가 스스로 짚은 약점이 실제로 결론을 비틀었다.
- **판단:** 기법 사전으로는 가치가 높다. 수치·형태·배경처럼 확인 가능한 사실 주장은 파일 실측으로 재검증한 뒤에 쓰는 게 맞다.

### 역할 분담 제안
Grok은 파일 확보와 실측, Muse는 프롬프트 기법 분석이 강하다. 같은 레퍼런스를 두 번 따로 분석하기보다 **하나의 레퍼런스 ID 아래 두 레이어로 합치는 것**이 좋다고 본다 (Grok 카드 파일명 ↔ Muse 항목 번호 교차 링크부터 시작). 현재 두 소스는 서로를 참조하지 않는다.

## 2. 신뢰도(★) 체계에 대한 의견

- Muse의 ★는 "독립 사례 수"를 표방하지만, 같은 저자(@jeong_do_ryeong)의 글을 독립 사례로 셌다(evidence §4). 한 사람의 프롬프트 작법이 반복된 것은 **재현성의 증거가 아니라 스타일의 증거**다. 저자 기준으로 다시 세면 #8·#14·#20·#22는 ★다. 다만 #20 POSITIVE LOCKS는 레포에 다른 출처(compiled-video-prompt-anatomy)가 있어 ★★로 볼 수 있다.
- 또 ★는 "그 기법이 쓰인 게시물 수"이지 "그 기법이 효과가 있었다는 증거"가 아니다. Muse 스스로 방법론 문서 §2.1·§2.2에서 생존자 편향을 지적했는데, 동의한다. 승격 게이트는 Somni 제안 5-5처럼 **우리 렌더러에서 A/B 1회 이상**을 필수로 하는 게 맞다고 본다.

## 3. 채택 권고

### 지금 채택 권고 (저비용, 우리 WanGP/H3 단일 클립에도 적용)
1. **레퍼런스 분석 규칙: 프롬프트 값과 파일 실측값을 칸을 나눠 기록.** 두 값이 다르면 둘 다 남긴다. 해상도·길이·컷 시각·형태처럼 확인 가능한 항목은 ffprobe나 scene detect로 채운다. 이번에 확인된 불일치 6건(E1~E6)이 모두 이 규칙으로 막을 수 있는 유형이었다. → `docs/reference-extraction.md` 보강.
2. **provenance 확인 단계.** 게시물 페이지에 영상이 여러 개면 본문, 캐러셀, 댓글, 관련 스레드 중 어디서 왔는지 기록한다(E1 재발 방지). Grok 수집 절차에 추가.
3. **근거 태그 measured / authored** (Muse 후보 #31·#32, Somni 제안 5-1): Master Spec의 결정마다 근거 출처를 붙인다.
4. **실패 출처를 명시한 네거티브** (#24): `docs/director-memory/failures.md`와 연결한다.

### 조건부 (실험 1회 후 판단)
- **관계형 부정문** (#22, "no X before/without Y"): 사실상 단일 저자 기법이다. 프롬프트 컴파일러에서 A/B 1회.
- **Self-POV 락** (#39, "camcorder never appears"): 노아·아오이 브이로그 작업에 바로 시험할 가치가 있다.
- **컷별 오디오 켜기/끄기** (#40): 오디오를 생성하는 외부 엔진(Grok Imagine 등)에서만 해당.

### 보류
- **컷·비트표 문법** (#13~#16): Seedance·Dola 같은 멀티샷 엔진 전용이다. 컷마다 따로 생성하는 우리 WanGP 흐름에는 직접 해당하지 않는다.
- **#15 "비트표는 순서만 신뢰, 절대 시간 쓰지 말 것"은 현재 문구로 승격하면 안 된다.** E4 실측으로는 뒤쪽 두 컷이 ±0.06s로 지켜졌고, 어긋난 것은 앞쪽 스팅어가 늘어나고 중간이 압축된 부분이다. 1건 기준으로 말할 수 있는 건 "절대 시간은 보장되지 않으니 실측으로 확인하라" 정도다. "절대 시간 금지"는 과한 일반화다.

### 별도 결정 필요
- **음악 → LLM 시나리오 → 프롬프트 파이프라인** (#18, Somni 제안 5-4): 규칙이 아니라 프로젝트다. 방향은 사용자의 장기 목표와 맞지만 `docs/current-priorities.md`에서 우선순위를 정할 일이다. 근거 사례 #37도 결과물의 타이밍이 프롬프트와 어긋났다는 점(E4)을 함께 고려해야 한다.

## 4. 불확실한 점 (내 판단의 한계)

- E5: Muse가 다른 배포본(세로 크롭)을 받았을 가능성을 완전히 배제하지 못했다.
- E6: 거울벽 부재는 2초 간격 샘플 기준이다. 오류라기보다 "확인 안 됨"이 정확하다.
- E1: 드럼 영상2(10.11s)는 보지 않았다. Muse 분석의 결론 자체는 영상1 기준으로 타당하다고 본다.
- Grok "Soft" 정리: 모호한 잔여 약 28곳은 판단하지 않고 남겼다. 규칙이 드물게 정상 용례를 지웠을 가능성이 있다(백업과 비교 가능).
